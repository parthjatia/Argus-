# Learning notes

Short, beginner-friendly notes on each core component: **how it works** and **what would break
without it**. Code links point to the main file for each part.

---

## 1. API key auth (`server/app/auth.py`)

**How it works**

1. The SDK sends `X-API-Key: argus_…` with every request.
2. The server hashes the key with SHA-256 and looks up the hash in `api_keys`
   (`WHERE key_hash = … AND revoked_at IS NULL`). The `UNIQUE` index makes this one fast lookup.
3. Found → we now know the `project_id`. Not found, missing or revoked → `401`.
4. This is a FastAPI **dependency** (`require_project`): a function FastAPI runs before the
   endpoint, whose return value (the `project_id`) is handed to the endpoint.

**Why hash keys?** The database only stores hashes, so a leaked database contains no usable keys.
SHA-256 (fast) is fine because keys are 256-bit random values that can't be guessed; slow hashes
like bcrypt are for human passwords. A deterministic hash also lets us look keys up by index.

**What would break without it**

- Without the dependency: anyone could write data into any project.
- If `project_id` came from the request body instead of the key: a client could simply claim to be
  another project. The body's `project_id` is ignored on purpose (there is a test for this).
- Without `revoked_at IS NULL`: revoking a leaked key would do nothing.
- With different messages for "unknown" and "revoked": attackers could learn which keys once existed.

## 2. Ingest endpoint and validation (`server/app/api/ingest.py`, `server/app/schemas.py`)

**How it works.** Checks run cheapest first and stop at the first failure:

| Step | Fails with | Why this order |
|---|---|---|
| 1. Body size ≤ 5 MB (`Content-Length`, and counted while reading) | `413` | Don't even read a huge body |
| 2. API key | `401` | Strangers learn nothing about our format |
| 3. Pydantic validation (`IngestBatch` → `SpanIn`) | `422` | Bad data never reaches the database |
| 4. Insert | `202`, or `503` if Postgres is down | |

- Pydantic models describe valid data: UUIDs, allowed `kind`/`status` values, timestamps **with**
  a timezone, `end_time >= start_time`, `model` required for `generation`, 1–1,000 spans.
- One invalid span rejects the whole batch (all or nothing).
- We parse the body ourselves (`model_validate_json`) instead of letting FastAPI do it, because
  FastAPI parses the body **before** running dependencies, which would make bad JSON return 422
  before the key is checked.
- **4xx vs 5xx matters for the SDK:** 4xx = "your request is wrong, don't retry";
  5xx (our `503`) = "temporary problem, retry with backoff".

**What would break without it**

- Without the size limit: one client could send a 2 GB body and exhaust server memory.
- Without validation: bad rows crash the insert (500), or worse, get stored and break the dashboard.
- Without `AwareDatetime`: a timestamp with no timezone could be read as the wrong hour.
- Without the `503` handler: a database outage would surface as a generic `500`.

## 3. Idempotent inserts (`server/app/storage.py`)

**The problem.** The SDK sends a batch; the server stores it; the `202` reply gets lost. The SDK
sees a timeout and **retries** the same batch. That retry is correct behaviour, so the server must
handle receiving the same span twice.

**How it works**

- Every span has an ID generated by the SDK (UUIDv4), so a retried span has the **same** ID.
- `spans` has `PRIMARY KEY (project_id, id)`. Postgres keeps an index of every pair and refuses
  a second row with the same pair.
- `INSERT … ON CONFLICT (project_id, id) DO NOTHING` turns "refuse with an error" into
  "skip this row quietly and continue". Sending a batch once or ten times gives the same result.
  This property is called **idempotency**.
- Two identical requests at the same moment are safe too: the second insert waits for the first
  transaction, sees the row, and skips it.
- The first stored version wins; a "duplicate" with different content is ignored.
- `(project_id, id)` rather than just `id`: the same span ID in another project is a different
  row, so one project can never block another project's spans.
- The whole batch is one transaction: stored completely or not at all.

**What would break without it**

- Without `ON CONFLICT … DO NOTHING`: the retry hits a duplicate-key error, the whole batch fails
  with 500, the SDK retries again and fails again, forever.
- With a random server-generated ID instead of the SDK's ID: every retry stores a **second copy**,
  doubling costs and spans in the dashboard.
- With `PRIMARY KEY (id)` only: project B could send a span with project A's ID first, and A's real
  span would be silently skipped.
- Without the transaction: a failure halfway would leave half a batch stored.
